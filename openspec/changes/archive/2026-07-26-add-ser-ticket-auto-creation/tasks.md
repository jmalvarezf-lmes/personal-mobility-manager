## 11. Fixes from ad-hoc 4R review (post-implementation)

An informal 4R review (risk/resilience/readability/reliability, run outside the native gentle-ai review lifecycle, per explicit user instruction) surfaced 9 findings on the diff produced by sections 1-10. This section fixes the ones the user asked to address; two findings (the retroactive-migration consent question, and the backend/frontend lock-table duplication) were left as-is, not part of this batch.

- [x] 11.1 **No idempotency check → duplicate real ticket creation.** Add `ParkingTicketRepository.find_active_for_vehicle(vehicle_id: UUID, at: datetime) -> ParkingTicket | None` (port + `PostgresParkingTicketRepository` impl: the vehicle's most recent ticket whose `end_date > at`, or `None`). Inject this repo into `DetermineSerTicketRequirement`; add a required `at: datetime` parameter to its `execute(zone, vehicle_id, at)` signature. After the enforcement-schedule check and before the exemption check, short-circuit to `False` (not required) if `find_active_for_vehicle` returns a ticket — deliberately vehicle-scoped, not zone-scoped (`ParkingTicket` doesn't store a zone number today; adding one is out of scope for this fix). Update both call sites (`SerTicketCreationTriggerHandler`, `SerTicketNotificationTriggerHandler`) to pass `at=event.received_at`. Update every existing test/mock of `DetermineSerTicketRequirement.execute` for the new signature, and add new tests for the active-ticket short-circuit (and for "no active ticket → proceeds as before").
- [x] 11.2 **Push-location endpoint blocks up to ~85s on provider HTTP calls.** Make `InMemoryEventPublisher.publish()` dispatch each subscribed handler asynchronously via an internal `concurrent.futures.ThreadPoolExecutor` (small fixed pool, e.g. 4 workers) instead of calling handlers inline — the calling thread (e.g. the HTTP push-location request) returns without waiting for handler completion. Log any exception that still escapes a handler (defensive only — handlers already self-contain their own exceptions) via `future.add_done_callback`, never let it vanish silently. Add `shutdown(wait: bool = True) -> None`, called from `app.py`'s lifespan shutdown block (alongside `parking_scheduler.stop()`). Add a test-only synchronization helper (e.g. `wait_for_idle(timeout: float = 5.0) -> None`) so tests can deterministically wait for async dispatch to finish instead of sleeping. Update `test_in_memory_event_publisher.py`'s tests (including the one literally named `test_subscribed_handler_invoked_synchronously_on_publish`) to assert eventual delivery via that helper. Update the "synchronous" claims in `EventPublisher`'s port docstring and in the affected handler docstrings that describe the previous synchronous-dispatch contract.
- [x] 11.3 **Charged-but-unpersisted ticket looks identical to "nothing happened."** Add `SerTicketPersistenceError(Exception)` to `domain/exceptions.py`. In `CreateSerTicket.execute()`'s existing `except Exception: logger.exception(...); raise` block (around `self._ticket_repo.save(ticket)`), raise `SerTicketPersistenceError(...) from exc` instead of a bare `raise` — this is the one exception to design.md's "CreateSerTicket stays untouched," justified because only `CreateSerTicket` itself knows this specific case occurred. In `SerTicketCreationTriggerHandler._map_exception_to_reason`, add a branch mapping `SerTicketPersistenceError` to a new reason `"ticket_created_but_not_recorded"`. In `SerTicketNotificationTriggerHandler.on_ticket_creation_failed`, pass a new template kwarg `possibly_created: bool` (`True` only when `event.reason == "ticket_created_but_not_recorded"`) — do NOT pass `reason` itself into the template. Update both `ser_ticket_creation_failed/{en,es}.txt.j2` templates to branch on `possibly_created` via Jinja `{% if %}`: the existing generic "please create manually" text for `False`, and a distinct "a ticket may already have been created — check your provider account before creating another" text for `True`. Add tests for the new exception, the new reason mapping, and both template branches.
- [x] 11.4 **No metric for auto-creation.** Add a counter to `metrics.py` following the existing `record_notification_dispatch`-style pattern: `record_ser_ticket_auto_creation(outcome: str)` (label `outcome`, values `"created"`/`"failed"`), with its own `_meter.create_counter(...)` instrument. Call it from `SerTicketCreationTriggerHandler`: `outcome="created"` right before publishing `SerTicketCreated`, `outcome="failed"` right before publishing `SerTicketCreationFailed`. Add a test asserting both call sites.
- [x] 11.5 **Stale trace span name after rename.** In `SerTicketNotificationTriggerHandler.on_vehicle_location_updated`, rename the span from `"event_handler.ser_ticket_trigger"` to `"event_handler.ser_ticket_notification.on_vehicle_location_updated"`, matching its two siblings' naming scheme. Update the assertion in `test_ser_ticket_notification_trigger_handler_observability.py`. Leave `SerTicketCreationTriggerHandler`'s own span name (`"event_handler.ser_ticket_creation_trigger"`) as-is — it's a different class with its own single-event convention, not part of this rename.
- [x] 11.6 **Preferences cascade isn't atomic.** Add `UserPreferencesRepository.update_with_notification_cascade(user_id, default_ticket_duration_minutes, auto_create_ticket, preferred_notification_channel, notification_language, timezone, notification_cascade: list[tuple[str, bool]]) -> UserPreferences` (port + `PostgresUserPreferencesRepository` impl). The Postgres implementation opens exactly one `engine.begin()` block and performs the `user_preferences` UPDATE plus one `user_notification_preferences` UPDATE per `notification_cascade` entry (upserting via the same `ensure_defaults`-equivalent logic `_set_enabled` used, to handle a possibly-missing row) — all in that single transaction, so a mid-operation failure rolls back every write, not just some. Update `preferences.py`'s `update_preferences` to call this one method instead of `preferences_repo.update(...)` followed by three separate `_set_enabled` calls; remove `_cascade_notification_preferences`/`_set_enabled` once no longer used. Add a test forcing a failure partway through (e.g. mock the second UPDATE to raise) and asserting the first UPDATE's effect is also rolled back.
