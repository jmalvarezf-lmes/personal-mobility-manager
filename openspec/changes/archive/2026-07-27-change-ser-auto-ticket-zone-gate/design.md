## Context

`SerTicketCreationTriggerHandler` and `SerTicketNotificationTriggerHandler` both subscribe to `VehicleLocationUpdated` and both currently gate on the same shape of check: skip if the distance since the vehicle's previous recorded location is below an effective threshold (the owner's `ser_zone_ticket_required` notification preference `config.threshold_m`, falling back to `DEFAULT_NOTIFICATION_MOVEMENT_THRESHOLD_METERS`, 50m by default).

For the notification handler this is correct — it's a "remind the user" feature, and a raw movement threshold is a reasonable proxy for "enough has changed to be worth telling the user about." For the creation handler it is the wrong signal: what matters for automatic ticket creation is whether the vehicle has entered a *different* SER zone than the one its previous known location was in, not how far it moved.

`DetermineSerTicketRequirement` already short-circuits to `False` when the vehicle has an active `ParkingTicket` (see `determine_ser_ticket_requirement.py`'s fix-11.1 idempotency check), but that check is **vehicle-scoped, not zone-scoped**, by its own docstring's admission: `ParkingTicket` stores no zone at all today, so "a vehicle with any active ticket anywhere is treated as not requiring a new one." This means the zone-transition gate alone is not sufficient: a vehicle with a still-active ticket for zone A that transitions into zone B would correctly be detected as a zone change by the new gate, reach `DetermineSerTicketRequirement`, and then be told "not required" anyway, because it still has *a* ticket — just not one for B. No ticket would ever be created for zone B. This gap has to be closed in this same change, by teaching `ParkingTicket` its own zone and making the short-circuit compare it against the zone being checked.

`RecordVehicleLocation.execute` already discards exact-duplicate coordinates before publishing `VehicleLocationUpdated` at all, so every event that reaches the handler represents at least *some* coordinate change — but GPS fixes carry positioning error (consumer/telematics-grade GPS is typically accurate to ~3-5m under open sky, worse in urban canyons), so "some coordinate change" is not the same as "the vehicle actually moved."

`SerZone.contains()` already has a `tolerance_m` parameter (default 0.0, but the injected repository call in `ser_zone_repo.py` passes `get_ser_zone_containment_tolerance_cm() / 100`, 50cm by default) added specifically to compensate for GPS boundary-precision error inside a single containment check (see the SER zone boundary precision bug: a real notification was missed because a point was 3.68cm outside a polygon under strict `covers()`). That tolerance operates *within* one zone lookup; it does not prevent a stationary vehicle's noisy GPS fixes from flipping between "zone A" / "no zone" / "zone B" across successive events. This design needs its own, separate noise floor for that.

## Goals / Non-Goals

**Goals:**
- Replace the creation handler's distance-threshold gate with a zone-transition gate: proceed to the requirement check only when the SER zone containing the current location differs from the SER zone containing the previous recorded location (comparing `(city_code, zone_number)`, with `None` representing "not in any zone").
- Suppress spurious zone-transition detection caused by GPS jitter on an otherwise-stationary vehicle, via a small, fixed, non-user-facing distance floor.
- Preserve existing behavior for a vehicle's first-ever recorded location (no previous location to compare against): it always proceeds to the zone check, matching the current handler's documented behavior for `previous is None`.
- Make `DetermineSerTicketRequirement`'s active-ticket short-circuit zone-aware, so an existing ticket for a *different* zone no longer suppresses creation of a new one for the zone the vehicle is actually in now.
- Leave `SerTicketNotificationTriggerHandler` and its distance-threshold gate completely untouched (its use of the now-zone-aware `DetermineSerTicketRequirement` changes in effect, not in code).

**Non-Goals:**
- Not adding any new user-facing preference or API surface — the noise floor is a technical/operational constant, same category as `SER_ZONE_CONTAINMENT_TOLERANCE_CM`.
- Not changing zone containment tolerance (`SER_ZONE_CONTAINMENT_TOLERANCE_CM`) itself, nor `SerZone.contains()`.
- Not backfilling zone data for `ParkingTicket` rows created before this change — they keep `city_code`/`zone_number` as `None` and are handled by a fail-safe (see D5).
- ~~Not changing `ParkingTicketRepository.find_active_for_vehicle`'s own vehicle-scoped *query*~~ **Revised after 4R review (see D5 and the Risks section):** the query itself does need to change — see below.

## Decisions

**D1 — Recompute the previous zone rather than caching a last-known zone.**
The handler already fetches the vehicle's previous recorded location via `VehicleLocationRepository.get_previous`. Zone comparison is done by calling the existing `FindContainingSerZone.execute` twice per event — once for the previous location's coordinates (when a previous location exists), once for the event's coordinates — and comparing `(zone.city_code, zone.zone_number)` (or `None`) for equality.

Alternative considered: persist a "last-known SER zone" per vehicle (new column or table), updated each time the handler runs, avoiding a second spatial lookup. Rejected for this change: `VehicleLocationUpdated` events are driven by a 5-minute default poll interval (`VEHICLE_POLL_INTERVAL_MINUTES`), not a high-frequency stream, so the extra spatial query is cheap; the cached-zone approach adds new persistence surface (a port, a repository method, a migration) for a marginal saving. Confirmed with the user as the preferred approach.

**D2 — A fixed, technical, env-var-only GPS-noise floor precedes the zone comparison.**
Before doing either zone lookup, the handler computes the distance between the previous recorded location and the event's coordinates (skipping this check entirely, like today, when there is no previous location). If that distance is below a floor, the handler skips without looking up either zone — the fix is treated as noise, not movement.

The floor defaults to **10 meters** (raised from an initial 5m — see "Revised after 4R review" below) and is read from a new environment variable, `SER_TICKET_CREATION_ZONE_CHANGE_FLOOR_METERS`, via a new `config.py` accessor, `get_ser_ticket_creation_zone_change_floor_meters()`, following the exact int-with-fallback style of `get_ser_zone_containment_tolerance_cm()`. Distinct from the notification handler's user-configurable, much larger (50m default) movement threshold, which answers a different question ("has the user moved enough to want a reminder").

Alternative considered: reuse `DEFAULT_NOTIFICATION_MOVEMENT_THRESHOLD_METERS` or the owner's `ser_zone_ticket_required` `config.threshold_m` (what the handler does today). Rejected: that value is tuned for "worth notifying the user," not for "is this GPS noise" — conflating the two would either make the floor too large (missing genuine zone entries after a short drive) or require users to reason about a purely technical concern. Explicitly requested by the user to be env-var-only, not user-configurable, "as it is difficult to explain."

**Revised after 4R review:** the initial 5m default was chosen on the premise that `VehicleLocationUpdated` events arrive at most every 5 minutes (the pull scheduler's default poll interval). A resilience-lens review found this premise incomplete: `POST /vehicles/{token}/location` (the push ingestion path) was rate-limited to 60/minute — up to ~1 event/second — independent of the poll interval, so ordinary GPS jitter (routinely exceeding 5m) could clear the floor on nearly every pushed event for a vehicle sitting near a zone boundary. Two changes address this together: the floor is raised to **10 meters** (still far tighter than the notification handler's 50m, but a larger buffer against jitter), and the push endpoint itself now also rate-limits per vehicle token to **1/minute** (see the `vehicle-location-push` capability's updated requirement) — capping how often this gate can even be evaluated for a given vehicle, regardless of how noisy its GPS is.

**D3 — Zone equality is by `(city_code, zone_number)`, treating `None` as its own state.**
Two zone lookups are "the same zone" only if both are `None`, or both are non-`None` with matching `(city_code, zone_number)`. Any other combination (`None` → a zone, a zone → `None`, or zone A → zone B) counts as a transition and proceeds to `DetermineSerTicketRequirement`. This mirrors how `DetermineSerTicketRequirement` and the exemption repository already identify a zone (by `city_code` + `zone_number`, not object identity or geometry).

**D4 — `ParkingTicket` gains `city_code: str | None` and `zone_number: str | None`, populated at creation, `None` only for legacy rows.**
Every code path that constructs a `ParkingTicket` today already has the containing `SerZone` in hand at that point: `ElParkingSerTicketProvider.create_ticket` calls `self._ser_zone_repo.find_containing(location)` (`provider.py:124`) before building the request, purely to resolve ElParking's own town/zone/rate identifiers — the zone this change needs is already sitting in a local variable there, so no new lookup, API call, or provider-side change is required, only threading `ser_zone.city_code`/`ser_zone.zone_number` into the returned `ParkingTicket`.

The fields are typed `str | None` (not `str`) because rows created before this change genuinely have no recoverable zone — there's no reliable way to reconstruct which zone an already-created ticket was for after the fact. This mirrors the existing `provider_reference: str | None` field's rationale (a value that's always populated by new writes but can be legitimately absent). The new database columns are nullable for the same reason; no backfill is attempted.

Alternative considered: derive the ticket's zone lazily at read time by re-running `FindContainingSerZone` against the vehicle's location history around `created_at`. Rejected: fragile (depends on having a location fix close enough to `created_at`), and unnecessary — the zone is already known for free at write time.

**D5 — The active-ticket short-circuit becomes zone-aware, checking *every* active ticket the vehicle holds, not just one; a legacy `None`-zone ticket still short-circuits unconditionally (fail-safe).**

**Revised after 4R review — see the corrected version below.** The first version of this decision compared the current zone against the single ticket returned by `ParkingTicketRepository.find_active_for_vehicle` (its existing query: the vehicle's one ticket with the latest `end_date` among still-active ones). Two independent review lenses (reliability and risk) found this unsafe: this change is precisely what makes it possible for a vehicle to hold *multiple* concurrently-active tickets in different zones for the first time (previously any active ticket blocked all creation, so at most one could ever be active). A vehicle cycling zone A → zone B → zone A while both tickets are still valid would have the zone-A check compare against ticket B — if B has a later `end_date` than A (the ordinary case, since B was created after A with a similar duration) — the mismatch would fail to short-circuit and create a duplicate, real, paid third ticket for zone A even though ticket A is still valid. This was not a rare edge case; it was the expected shape of any A→B→A drive.

**Corrected design:** `ParkingTicketRepository` gains `find_all_active_for_vehicle(vehicle_id, at) -> list[ParkingTicket]`, replacing `find_active_for_vehicle`'s single-ticket return — it returns *every* one of the vehicle's tickets still active at `at`, not just the one with the latest `end_date`. `DetermineSerTicketRequirement.execute` then short-circuits to `False` if **any** ticket in that list either:
- has `(city_code, zone_number) == (None, None)` (a legacy, pre-migration ticket — we can't know what zone it covers, so the fail-safe is to keep suppressing new creation for it rather than risk a duplicate paid ticket), or
- matches the zone being checked's `(city_code, zone_number)` (already covered by that specific ticket).

Otherwise (no active ticket matches, known or legacy) — it does **not** short-circuit; it falls through to the ambient-label/exemption chain exactly as if the vehicle had no active tickets at all.

This is a deliberate asymmetric fail-safe: an unrecoverable-zone ticket → assume covered (avoid double-charging), a real ticket for a genuinely different zone → assume not covered (the whole point of this change) — now evaluated per-ticket across the vehicle's full active set, not against a single arbitrarily-selected one.

This use case is shared with `SerTicketNotificationTriggerHandler`, so the "you need a ticket" notification path gets the same fix as a side effect — previously suppressed incorrectly for a vehicle that already had a ticket for a different zone, it will now correctly fire again. This is treated as a welcome consequence of fixing a shared dependency, not scope creep, since it's the same underlying defect.

## Risks / Trade-offs

- **[Risk, CONFIRMED and fixed by 4R review — see corrected D5] A vehicle bouncing between two adjacent zones right at their shared boundary, each fix past the noise floor, could trigger a `DetermineSerTicketRequirement` check on every event, and — under the original single-ticket D5 — could create a duplicate paid ticket for a zone it already has a still-valid ticket for.** → Fix: the active-ticket short-circuit now checks every one of the vehicle's active tickets (`find_all_active_for_vehicle`), not just the single most-recent-by-`end_date` one, so a matching ticket for the zone being re-entered is always found regardless of which other zones' tickets are also still active.
- **[Risk] Choosing a fixed default (10m) could be wrong for some GPS sources (e.g. a noisier OBD dongle) or right-sized for others (e.g. an integrated vehicle GPS).** → Mitigation: exposed as an env var precisely so it can be tuned per deployment without a code change, while staying out of user-facing preference surface.
- **[Trade-off] Recomputing the previous zone doubles spatial zone lookups per event that clears the noise floor**, versus caching a last-known zone. → Accepted; see the next risk for why the assumed event frequency needed revisiting, and the mitigations adopted (raised floor + per-token push rate limit) rather than reversing this trade-off.
- **[Risk, CONFIRMED and mitigated by 4R review] The "low event frequency (5-minute default poll interval)" premise behind the original 5m floor does not hold for the push ingestion path**, `POST /vehicles/{token}/location`, which was rate-limited to 60/minute (up to ~1 event/second) with no per-vehicle floor of its own — so ordinary GPS jitter near a zone boundary could clear a too-small floor on nearly every pushed event, and if a prior `CreateSerTicket.execute` call had raised `SerTicketPersistenceError` (provider already charged, our own record failed to persist), repeated jittery transitions could retry real ticket creation against the provider with no cooldown anywhere in the codebase. → Fix: the floor is raised to 10m, and the push endpoint now also rate-limits per vehicle token to 1/minute (see the `vehicle-location-push` capability), capping the maximum rate at which this gate can be evaluated for any single vehicle regardless of GPS noise.
- **[Risk, accepted, not fixed] `PostgresSerZoneRepository.find_containing` is an uncached, unfiltered full-table scan with per-row Shapely `contains()` computation in Python — now reached (up to twice per event) more often than the original design assumed.** → Not fixed in this change: introducing a cache (or a spatial index / bounding-box prefilter at the query level) is the correct long-term fix, but is a larger, separate piece of work. The 10m floor and 1/minute per-token push limit adopted above bound how often this cost can be incurred per vehicle, which is judged sufficient for now.
- **[Risk] The legacy fail-safe means a vehicle whose currently-active ticket predates this migration will not get an automatically-created ticket for a genuinely new zone until that legacy ticket expires.** → Mitigation: accepted as a bounded, self-healing transition cost — every ticket created going forward carries its zone, so this only affects tickets already active at deploy time, not new ones.

## Migration Plan

One additive, nullable-column database migration: add `city_code` and `zone_number` (both nullable `Text`) to `parking_tickets` via a new Alembic revision (`alembic revision --autogenerate` after updating `tables.py`, per the `schema-migrations` capability). No backfill — existing rows keep both columns `NULL`, handled by the D5 fail-safe. Deploying is a normal code release (migration + code in the same rollout, migration first); rollback is a normal revert plus `alembic downgrade -1` if the column needs to be removed, safe because nothing reads/writes it outside this change's own code paths.

## Open Questions

None outstanding — confirmed with the user: recompute (not cache) the previous zone, use a 5m env-var-only default floor, and extend `ParkingTicket` with zone fields so the active-ticket short-circuit can be scoped to the actual zone instead of the whole vehicle.
