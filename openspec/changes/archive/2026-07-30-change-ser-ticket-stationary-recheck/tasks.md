## 7. Fixes from 4R review

A post-implementation 4R review (readability, reliability, resilience, risk) found one CRITICAL issue, two WARNINGs, and one SUGGESTION. All four were approved and fixed in this section.

- [x] 7.1 **(Fix #1, CRITICAL — financial-risk regression, bounded retry)** `SerZoneRecheckGate`'s "no active ticket → always recheck" branch cannot distinguish a genuinely uncovered vehicle from one where `CreateSerTicket.execute` already succeeded with the provider (real charge) but failed to persist the `ParkingTicket` row — with no row to change that answer, the gate keeps signalling "recheck" on every poll, so `SerTicketCreationTriggerHandler` would keep calling `CreateSerTicket.execute` again, repeating the real charge. Wrapped `self._ticket_repo.save(ticket)` in `create_ser_ticket.py` with a bounded retry: `_TICKET_SAVE_MAX_ATTEMPTS = 3` total attempts, `_TICKET_SAVE_RETRY_DELAY_SECONDS = 0.2` between attempts (stdlib `time.sleep`, no new dependency), as simple module-level constants (mirrors `_MAX_FUTURE_SECONDS` in `record_vehicle_location.py` — an internal technical constant, not a per-deployment tuning knob). This is deliberately not a full fix for extended outages (rejected as disproportionate) — it only closes the realistic transient-failure window (query timeout, deadlock, momentary connection blip). Updated `SerTicketPersistenceError`'s docstring/raise-site comments to note the retry already happened.
- [x] 7.2 Added tests in `tests/application/use_cases/test_create_ser_ticket.py`: `test_ticket_repo_save_succeeds_after_transient_failures_no_exception_raised` (save fails twice then succeeds — ticket persisted, no exception) and renamed/extended `test_ticket_repo_save_failure_is_logged_and_raised_as_persistence_error_after_exhausting_retries` (all attempts fail — `SerTicketPersistenceError` still raised, `save_calls == 3`). Both monkeypatch `_TICKET_SAVE_RETRY_DELAY_SECONDS` to `0` so no real sleep delay slows the suite.
- [x] 7.3 **(Fix #2, WARNING — resilience/observability)** `SerZoneRecheckGate.evaluate` had no logging of its own; both callers logged an identical generic "no recheck needed" line regardless of which skip reason applied, losing the specificity the original inline handler code had (distance-vs-floor, zone-unchanged). Added specific `logger.info(...)` calls directly inside `SerZoneRecheckGate.evaluate` at each of its two skip points (movement below `movement_floor_meters` — logs the distance and floor; SER zone unchanged — logs the vehicle id). Removed the now-redundant generic "SerZoneRecheckGate signalled no recheck needed" log lines from `ser_ticket_creation_trigger_handler.py` and `ser_ticket_notification_trigger_handler.py`. No new metrics counter added — explicitly out of scope (wasn't present before the refactor either).
- [x] 7.4 Added `test_movement_below_floor_logs_specific_reason` and `test_zone_unchanged_logs_specific_reason` to `tests/application/use_cases/test_ser_zone_recheck_gate.py`, using the `caplog` fixture convention already used in this codebase (see `test_create_ser_ticket.py`).
- [x] 7.5 **(Fix #3, WARNING — test-coverage gap)** No test proved `VehicleLocationRepository.get_previous` is never called when the vehicle has no active ticket (the spec-mandated ordering: active-ticket check strictly before the previous-location fetch). Added `test_no_active_ticket_never_calls_get_previous_or_resolves_zone_twice` to `tests/application/use_cases/test_ser_zone_recheck_gate.py`, asserting `get_previous_calls == []` and `find_containing.calls` has exactly one entry (the event's own coordinates).
- [x] 7.6 **(Fix #4, SUGGESTION — readability)** `self._find_containing_ser_zone.execute(GeoLocation(lat=..., lng=...))` was repeated verbatim 3 times in `SerZoneRecheckGate.evaluate`. Extracted a private helper `_zone_for(self, lat: float, lng: float) -> SerZone | None` and used it at all 3 call sites (2 for the event's own coordinates, 1 for the previous location's coordinates).
- [x] 7.7 Added a short note to `design.md`'s "Risks / Trade-offs" section documenting the retry mitigation now in place for the `SerTicketPersistenceError` interaction.
- [x] 7.8 Ran `make test POSTGRES_DSN=` and `make coverage POSTGRES_DSN=` again (override forces the clean integration-test-skip path — this repo's `.env` points `POSTGRES_DSN` at a docker-compose hostname not reachable locally); confirmed fully green, `domain/` at 100%, `application/` at or above 80%.
